Spring Boot 事务失效的六种常见场景

这周在做课程项目的转账模块时撞上了经典问题：@Transactional 明明加了，异常也抛了，数据库却照样写入了一半。排查了一晚上，把 Propagation、代理机制和 rollbackFor 的文档翻了一遍，顺手整理出六个事务失效的高频场景——面试爱问，写业务更爱踩。

一、方法不是 public

Spring 的事务是基于动态代理实现的，默认只有 public 方法才能被代理拦截。给 private 或 protected 方法加 @Transactional，注解会被静默忽略，不报错、不回滚，是最阴险的一类失效。

二、同类内部调用（自调用）

事务藏在代理对象里，而 this.xxx() 调用的是原始对象，绕过了代理——所以被调用方法上的事务注解完全不生效：

@Service
public class OrderService {

    public void createOrder(Order order) {
        // this 调用绕过了代理，saveOrder 上的事务不生效
        this.saveOrder(order);
    }

    @Transactional(rollbackFor = Exception.class)
    public void saveOrder(Order order) {
        orderMapper.insert(order);
        accountMapper.deduct(order.getAmount());
    }
}

修复方式：把 saveOrder 拆到另一个 Bean 里注入使用，或者通过 AopContext.currentProxy() 拿到代理对象再调用。我自己的原则是干脆不写「事务方法包事务方法」的结构，让事务边界落在 Service 的最外层入口上。

三、异常被 try-catch 吞掉

事务回滚的前提是异常穿过了代理。半路把异常 catch 住，代理根本感知不到出过问题：

@Transactional(rollbackFor = Exception.class)
public void transfer(Long from, Long to, BigDecimal amount) {
    accountMapper.deduct(from, amount);
    try {
        riskClient.check(from);            // 远程风控校验
    } catch (Exception e) {
        log.warn("风控校验失败，忽略", e);   // 异常被吞，事务照常提交
    }
    accountMapper.add(to, amount);
}

如果确实要捕获后继续处理，必须在 catch 里手动标记回滚：

catch (Exception e) {
    log.warn("风控校验失败，回滚", e);
    TransactionAspectSupport.currentTransactionStatus()
            .setRollbackOnly();
}

四、受检异常默认不回滚

这是最容易忽略的一条：默认只有 RuntimeException 和 Error 触发回滚，受检异常（Exception 子类）默认提交：

// 默认只回滚 RuntimeException 和 Error
@Transactional
public void settle(Bill bill) throws Exception {
    billMapper.insert(bill);
    if (bill.isAbnormal()) {
        throw new Exception("账单异常");   // 不会回滚！
    }
}

解法是把 rollbackFor = Exception.class 写成肌肉记忆，团队里直接约定成代码规范。

五、表引擎不支持事务

老项目里常见的坑：MySQL 表用的是 MyISAM 引擎，压根不支持事务，应用层配置得再对也没用。确认方式是看表结构：

SHOW TABLE STATUS WHERE Name = 't_bill';
-- Engine 一列如果是 MyISAM，改成 InnoDB：
ALTER TABLE t_bill ENGINE = InnoDB;

六、多线程调用

事务上下文绑定在 ThreadLocal 上，跨线程就丢了。在事务方法里起子线程去写库，那段写入不受外层事务管辖，回滚时它纹丝不动。需要异步写库时，要么让子线程自己开事务，要么改用消息表 + 定时补偿这类最终一致方案。

总结

场景根因解法
方法非 public代理只增强 public 方法改 public，或拆 Bean
自调用this 绕过代理拆 Bean / 编程式事务
异常被吞代理感知不到异常重新抛出或 setRollbackOnly
受检异常默认回滚规则不含 ExceptionrollbackFor = Exception.class
MyISAM 表引擎不支持事务换 InnoDB
多线程事务上下文不跨线程子线程自管事务 / 最终一致

最后记一条通用排查思路：事务失效时，先确认「注解所在方法是否被代理正常拦截」（一、二、六），再确认「异常是否按预期穿过了代理」（三、四），最后看存储层（五）。按这个顺序走，基本十分钟内能定位。

框架的便利都是明码标价的：不理解注解背后的机制，它失效时你就只能干瞪眼。
